Local changes to the vendored check scripts (all to be upstreamed):

* absolute imports (`from _report import`) rewritten to package-relative
  (`from ._report import`); `run_checks.py` (the multi-module publisher)
  dropped in favour of `fprime_auto_checklist.runner`;
* `check_fpp_generate.py`: only `.fpp` files (not `.fppi`) are passed to
  `fpp-check` as top-level inputs;
* `check_sdd_port_table.py`: `Svc::Sched` in the SDD matches `Svc.Sched` in FPP;
* `check_hardware_run.py`: inside a git checkout an unknown recorded commit
  fails the check (previously exit 128 was treated as "not a repo");
* `check_ci_status.py`: `--repo`/`--sha` are validated before building the API URL.
* `_requirements.py`: HTML anchors (`<a id=...></a>`) are stripped from cells and
  only exact ID headers (`ID`, `Req ID`, `Requirement`) start a requirements
  table, so verification matrices with a `Requirements` column are not parsed
  as requirements;
* `check_sdd_sections.py` (D9, item 2.2): a fenced ASCII-art block (box-drawing
  glyphs) under a design heading counts as a block diagram;
* `check_include_dependencies.py` (I1, item 3.1): with `--build-cache` (passed by
  the runner) includes are resolved on the build's include path from
  `compile_commands.json`, module names come from the project/framework roots, and
  dependencies FPP adds itself (`fpp-cache/direct.txt`, `framework.txt`) plus the
  implicit `Fw_Types` are not reported;
* `check_leaks.py` (U4, item 4.4): `fprime-util check --leak` does not exist in
  fprime-tools; the check now runs the module's `*_ut_exe` from the `-ut` build
  cache (building it with `fprime-util build --ut` when missing) under
  LeakSanitizer when the executable is AddressSanitizer-instrumented (the F Prime
  default for native UT builds, incompatible with valgrind) or under valgrind
  otherwise;
* `check_coverage_threshold.py` (U5, item 4.5): reads `coverage/summary.txt`
  (gcovr `--txt` table, `TOTAL` row) written by `fprime-util check --coverage`
  before falling back to its own gcovr run;
* `check_req_ports.py` (R6, item 2.13): a port counts as having a known use-case
  when a requirement names it, when its SDD port-table row has a description,
  or when it is a companion (`<base>Complete|Done|Callback|Response`) of a
  covered port -- requirements describe behaviour and rarely name ports;
* `_sdd.py` / `check_sdd_port_table.py`: a cell naming several ports/channels
  (`pingIn / pingOut`, `A, B`) is split; `Type` may carry the return type
  (`Fram.Request → Fram.Status`); special ports named in the FPP (product
  get/send, internal ports) are not reported as unknown.

The CodeQL queries are unmodified; `codeql-pack.lock.yml` is generated by
`codeql pack install` and committed to pin the pack's dependencies.

Refresh with `tools/vendor.sh <fprime-checkout> <fprime-actions-checkout>`.
